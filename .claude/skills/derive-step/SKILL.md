# 導出ステップの実行

`<SRC>` から `<DST>` を導出する。引数がなければ、README の derivation path と
既存フォルダを突き合わせて「次に作るべきフォルダ」を提案し、確認を取る。

## 大前提

**このリポジトリは一種の証明であり、隣接ステップの差分が「正当性の自明な変換」で
あることがその本体である。** `make test` を通すことが目的ではない。
詳細は CLAUDE.md の「最重要ルール」を読むこと。

## 手順

### 0. パスの確認

- `README.md` の `## Derivation path` 直下、最初の `###` セクションを読む。
- `<SRC>` → `<DST>` がそのパス上で**隣接**していることを確認する。
  隣接していなければ中断してユーザーに確認する（ステップの飛ばしは証明の穴になる）。
- `<DST>` が既に存在する場合も中断して確認する。

### 1. 変換内容を先に言語化する

コードを触る前に、**何の変換をかけるのか**を一文で述べる。
CLAUDE.md の対応表で論文の step 番号を引き、論文の該当節
（`/Users/chiaki/Documents/git/ochacaml4d.paper/jssst_journal/derivation-step{1,5,8,10}.tex`）に
記述があればそれを読む。

言語化できない場合、その変換は自明ではない。手を止めてユーザーに相談する。

### 2. 無変更コピー

```bash
cp -r <SRC> <DST>
cd <DST> && make test
```

テストが通ることを確認する（通らなければ `<SRC>` 側に問題があるので報告して中断）。

```bash
git add <DST> && git commit -m "<DST>: derived from <SRC>"
```

**この無変更コピーを必ず独立したコミットにする。** これにより次のコミットの差分が
変換内容そのものになり、レビュー可能になる。

### 3. 変換の適用

- `<SRC>/eval.ml` を読み、**そこからの差分としてのみ** `<DST>/eval.ml` を書き換える。
- 継続や命令の型が変わる変換なら `<DST>/value.ml` も触る。それ以外のファイルは触らない。
- 前ステップに存在しないロジックを新規に書き起こさない。

### 4. 検証

```bash
cd <DST> && make test
```

**テストが失敗したときに、テストを通すための場当たり的な修正をしてはならない。**
失敗は次のいずれかを意味する:

- 変換が自明でない（＝そのステップは分割すべき、または別の変換を先にかけるべき）
- 変換をかける順番が間違っている
- `<SRC>` 側に未修正の問題がある（上流に遡って直す必要がある）

いずれの場合も、**原因の見立てをユーザーに報告して指示を仰ぐ**。

### 5. コミット

```bash
git add <DST> && git commit -m "<DST>: <かけた変換の説明>"
```

メッセージには**どの変換をかけたか**を書く（例: `eval9a: derived from eval8a` /
`eval2a: 継続の非関数化`）。既存のコミットメッセージの粒度と言語（日本語）に合わせる。

### 6. README の更新

derivation path に新しいフォルダが加わる場合、`README.md` の該当セクションを更新し、
そのステップで何をしたかの注釈を追記する。
